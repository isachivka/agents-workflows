# Plan: a conversation per run

Spec: [2026-10-18-run-chat-design.md](../specs/2026-10-18-run-chat-design.md).
Each task: test first (fails), code, `npm test` and `npm run typecheck` green, one commit.

**One deviation from the spec:** the conversation's address is kept in a `chats` table of the store,
not in `RunState.chat`. Opening a conversation is a network call outside the event chain; writing
its answer into the run's JSON would race a step committed meanwhile (a lost update). A table row
keyed by run is written once and read by anyone, with no race.

## Task 1 — store: a run's conversation

Files: `src/store.ts`, `test/store.test.ts`.

- `CREATE TABLE IF NOT EXISTS chats (run_id TEXT PRIMARY KEY, adapter TEXT NOT NULL, address TEXT NOT NULL)`.
- `chatOf(run): {adapter, address} | null`, `setChat(run, adapter, address)`,
  `runByChat(adapter, address): RunState | null`.
- Test: set, read back, find the run by its address; another adapter's address is not found.

## Task 2 — plugins: the `chat` capability

Files: `src/plugins.ts`, `src/check.ts`, `test/plugins.test.ts`.

- `Plugin.chat?: { open(run, ctx), post(address, msg, ctx), close(address, end, ctx) }`.
- `PluginCtx.message(m: {address, text, from})`; the host passes it to a new constructor option
  `onMessage(adapter, m)`.
- `host.chat(): {name, chat, ctx} | {error} | null`: the loaded plugins with `chat` whose name has a
  section in the config. Two → `{error: "two chat adapters are set up (a, b): keep one section in
  plugins.yaml"}`, and the same line in `loadErrors.chat` (Settings → Plugins).
- `checkDefs` reads the real plugin config (`readPluginConfig`), so `flow check` prints that line.
- Tests: none configured → null; one → it; two → the error; `ctx.message` reaches `onMessage` with
  the plugin's name.

## Task 3 — `flow say`

Files: `src/daemon.ts`, `src/http.ts`, `src/cli.ts`, `test/daemon-chat.test.ts` (new),
`test/http.test.ts`, `test/cli.test.ts`, `test/daemon-helpers.ts` (a `CHAT_PLUGIN` fake that
records `open/post/close` on `globalThis` and exposes its ctx).

- `Flowd.say({session?, run?, text, file?}): Promise<{ok} | {error}>`:
  run from `--run`, else `store.runBySession` (top of the stack); the root is found by following
  `parent`. No adapter → the spec's refusal; a `file` that does not exist → `no file <path>`.
  `chatFor(root)`: the stored address of the active adapter, else `open` once — concurrent callers
  share one promise per root — then `setChat`. Then `post`. Adapter errors come back as `{error}`.
- `POST /api/say` (400 without `text`); `flow say TEXT [--file PATH] [--run ID]`, the file made
  absolute against the CLI's cwd.
- Tests: two says open one conversation and post twice; a nested run's say goes to the root's
  conversation; no adapter → refused; missing file → refused; an adapter's `post` throwing comes
  back as the error; an address stored by another adapter is not reused.

## Task 4 — flowd's own messages

Files: `src/daemon.ts`, `test/daemon-chat.test.ts`.

- `needsYou(run)` pulled out of `runSummary` into a function both use.
- In `commit`, with the run as it was before (`store.getRun` before `saveRun`): on a root run whose
  `needsYou` turns true, post `<process> #<n> waits for you: <the wait's note, or the step's
  summary, or the run's reason>` (opening the conversation). For a nested run, the same into the
  root's. When a root run reaches a terminal status from an open one and has a conversation: post
  `done` / `failed: <reason>` / `stopped`, then `close`. In the background: a failure is logged and
  set as the adapter's `lastError`, never failing the run.
- Tests: a human step posts and opens; `flow wait --human` posts; the end of a run with a
  conversation posts and closes; the end of a run without one opens nothing; a failing `post` leaves
  the run as it was.

## Task 5 — the person's messages

Files: `src/daemon.ts`, `test/daemon-chat.test.ts`.

- `onMessage(adapter, {address, text, from})`: `store.runByChat` → the root; ended → reply
  `run <id> has ended`. The top of its stack: follow the current entry's `child` while it is open.
  Its current entry has an agent role → `store.enqueue(top, role, "<from> (<adapter>): <text>")`
  and `flush()`: the outbox types it when the agent's turn has ended and nobody is typing in the
  terminal, as it does step lines. No agent → reply `no agent is on a step now (<entry>: <kind>);
  write again when one is`.
- Tests: a message to a working run reaches its agent's session after the turn ends; to a nested
  run's conversation it reaches the child's agent; at a human step it is answered and not typed;
  to an ended run it is answered; an unknown address is logged only.

## Task 6 — the Telegram adapter

Files: `package.json` (`grammy`), `plugins/telegram.ts`, `test/telegram.test.ts`.

- As in the spec. The bot is created in `start` only when the config has `token`; without it the
  plugin does nothing. `apiRoot` from the config (default Telegram), so the test points it at a
  local fake Bot API (`node:http`) that records calls and serves `getUpdates` from a queue.
- `open` → `createForumTopic`; the name `<process> #<n> · <title>` cut to 128. `post` → `sendMessage`
  parts of ≤ 4096; with a file `sendDocument` (caption when ≤ 1024, else a message first). `close`
  → `closeForumTopic`. Bot API errors are rethrown with a hint for the usual ones (not enough
  rights → make the bot an admin with "manage topics"; chat not found → check `chat`).
- Incoming: `message` in `chat` with `message_thread_id`, from a user in `users` → `ctx.message`;
  others are logged.
- Tests: topic name and address; a 5000-character text is two messages; a document with a caption;
  close; an allowed user's message reaches `ctx.message`, a stranger's and one outside a topic do not.
